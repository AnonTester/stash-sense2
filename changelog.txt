  selection, pre-check, sort order, and displayed percentage all agree.

### 0.14.18 (sidecar only)
- Fix: `GET /recommendations/{id}` only pruned the single row it was
  called with when a scene_face_match recommendation's referenced scene
  no longer existed in Stash -- every scene_face_match "entry" the UI
  shows is actually several raw DB rows (one per detected person +
  candidate) sharing the same scene_id, grouped into one synthetic
  representative by `_group_scene_face_match_recommendations`. Deleting
  only the clicked representative row left its siblings behind, still
  `pending`, so the group reappeared (rebuilt from the survivors) on the
  next list load even though the UI had already shown "removed because
  scene no longer exists" and dropped it from view. Confirmed live:
  scene 11231 ("ps.ct4") had 18 raw rows; opening it deleted exactly one
  and left 17 behind. Fixed with a whole-group prune mirroring the one
  `duplicate_scenes` recommendations already had.
- Fix: scene face-match identification (`clustered_frequency_matching`,
  the default `matching_mode="frequency"` used by both the Scene Face
  Matches recommendation scan and manual scene identify, and
  `frequency_based_matching`, reached via `matching_mode="hybrid"`)
  displayed a person-cluster's *average* distance across every tracked
  frame instead of the *best* frame's distance that had actually
  qualified and ranked the candidate as the winner. A performer tracked
  across many frames only needs one or two good matches to correctly win
  identification (by design -- the gating/ranking logic is entirely
  best-frame-based), but weaker frames elsewhere in the same cluster
  (motion blur, side angles, partial occlusion) could drag the *average*
  distance past 1.0, displaying 0% confidence for a correct match.
  Confirmed live: several 30+ frame "Cristina Agave" clusters showed 0%
  despite being the right performer, while the same performer/database
  entry pairing showed 35-65% confidence in other scenes with fewer
  tracked frames -- i.e. more frames could make a correct match look
  *less* confident, the opposite of the frame-count bonus this same
  logic already rewards during ranking. Now shows the best frame's own
  distance, consistent with what selected the candidate in the first
  place.

### 0.14.14 (sidecar only)

  SQLite/usearch work (`apply_delta_db`) directly on the FastAPI event

  single jump from 0 to 100 -- the phase that most needed it, since it's
  routinely the slowest part of an update and previously the most opaque.

### 0.14.8 (sidecar only)
- Fix: Stop/Force Cancel didn't actually stop most analysis-based queue
  jobs (Upstream Performer/Tag/Studio/Scene Change Detection, Scene
  Stash-Box Tagger, Duplicate Performer/Scene File Detection). Root
  cause was in `jobs/analysis_jobs.py`'s generic `AnalysisJob` wrapper:
  it bridged the queue's live stop signal into the analyzer's own
  `is_stop_requested()` flag with a single snapshot check taken *before*

  so a Stop now actually halts these mid-run instead of only ever taking
  effect via Force Cancel (which kills the whole asyncio task outright,
  and did already work, just with no graceful/resumable option before
  this).

### 0.5.10
- Fix: VAAPI hardware acceleration now works correctly on AMD and Intel.
  The mwader/static-ffmpeg binary is fully static and cannot dlopen libva

  always failed with "Device creation failed: -12" regardless of what runtime
  libraries were installed. The fix uses a dual-binary approach: the static
  build (/usr/local/bin/ffmpeg) is used for CPU and CUDA modes, while VAAPI
  mode explicitly calls the system ffmpeg package (/usr/bin/ffmpeg), which is
  dynamically linked and correctly loads mesa-va-drivers at runtime. Both
  binaries are now installed in the container.

  Without them ffmpeg silently failed with "Device creation failed: -12" and
  marked every scene as an error. These packages are now installed in the runtime

  at scene 0. Progress counts also resume from the cursor value rather than
  jumping from 0 again.
