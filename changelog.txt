## 2026-09-02

### 0.27.0 (sidecar only)
- Fix: face detection/recognition now corrects for in-plane rotation
  ("roll") -- a source photo/frame can be genuinely stored sideways or
  upside-down (no EXIF orientation to recover) or a real candid pose
  (head tilted back), and while the detector's own confidence stays
  deceptively high across the full rotation range, the actual
  recognition embedding degrades badly past roughly 60-90 degrees of
  roll. Measures roll from the detector's own 5-point landmarks, rotates
  and re-detects, and iterates (up to 3 attempts, each correcting the
  previous attempt's own residual) until a re-detection's own roll comes
  back near zero -- a single-pass version left a tightly-cropped
  ("Select to identify" on just the head, not the full frame) upside-
  down photo only partially corrected and it matched the wrong
  performer with high confidence; the second pass converges. Falls back
  to the original detection whenever correction doesn't clearly
  converge within budget. api/embeddings.py mirrors stash-sense2-data-
  gen's own embed/embeddings.py exactly (same thresholds, same formula)
  since query-time detection must stay in lock-step with whatever
  produced the database's own stored embeddings.

### 0.22.0 (plugin only)
- Fix: "Select to identify" now pads the user's drawn selection by 40%
  on each side before sending it for identification. A selection drawn
  tight to just the face (the natural thing to do) reliably found NO face
  at all -- confirmed against the sidecar's own detector: SCRFD needs
  some surrounding context (hair/jaw/ears) to recognize a face pattern,
  independent of rotation. Doesn't help a face that's genuinely partial
  or at an extreme angle within the frame -- there's no missing context
  to add back for that -- but recovers the much more common "selection
  was just too tight" case. "Identify current frame" is unaffected (no
  user-drawn selection involved).

### 0.23.0 (sidecar only)
- Improvement: sprite-tile face detection now sizes the detector's input
  canvas to each scene's actual sprite-tile dimensions instead of forcing
  every tile onto the fixed 640x640 default. InsightFace's SCRFD detector
  letterboxes *every* input onto whatever fixed square canvas det_size
  specifies, so a ~160x90 sprite tile was paying the same full-canvas
  detection cost as a real video frame despite being far smaller --
  confirmed via a 500-scene/~40k-tile production benchmark to be ~3x
  faster overall (up to ~8x per-tile in steady state) with a small
  *positive* accuracy delta, not a tradeoff. Applies everywhere sprite
  tiles get detected: Fingerprint Missing, Refresh Outdated, and Face
  Recommendations.
- Feature: new "Use Sprite Tiles For Detection" setting (Settings ->
  Performance, on by default) lets sprite-tile detection be turned off for
  Fingerprint Missing, Refresh Outdated, and Face Recommendations
  background scans -- useful for comparing throughput/accuracy, or for
  deferring sprite coverage to a later run. Turning it off never deletes
  already-generated sprite data, it just stops generating more; read once
  at the start of each task run, so pausing and resuming an in-progress
  task after changing it takes effect on that resume.

### 0.17.0 (sidecar) / 0.16.0 (plugin)

### 0.16.1 (sidecar only)
- Feature: delta updates can now carry field-only changes to faces that
  already shipped in an earlier release -- e.g. gender/age inference or
  image_sha256 backfilled server-side after the fact (see
  stash-sense2-data-gen's build/export_delta.py). Previously the delta
  mechanism only knew about new/removed rows (crawl diffs, catalogue-
  source timestamps); a direct-UPDATE backfill script touching existing
  rows was invisible to it, so a sidecar preferring the (smaller, faster)
  delta path over a full re-download would silently never receive that
  kind of change. `delta_applier.py` applies these as a plain

  in the SQL, and application is tolerant of version skew either
  direction -- an older client applying a delta with a field it
  doesn't know about yet, or a newer client applying an older delta
  missing one it does, both degrade gracefully to whatever fields are
  actually in common, rather than erroring.

  performer is instead staged into that tab's own Performers field, the

  reloads automatically after the direct mutation (previously it didn't
  reload in that case at all, leaving the Details-tab cover stale).

  much worse: the "is an edit tab open" check only looked for a Save
  button anywhere in the DOM, but Stash's tabs (Details/Edit/Markers/...)
  stay mounted after switching away -- so once a scene's Edit tab had
  been visited even once, its now-hidden Save button kept being found
  from every other tab for the rest of the page's lifetime. Confirmed
  live: this caused an add clicked from the Details tab to silently
  stage into the hidden, inactive Edit tab instead of mutating directly,
  with no visible feedback at all. The check now also requires the Save

## 2026-06-05

### 0.5.10
- Fix: VAAPI hardware acceleration now works correctly on AMD and Intel.
  The mwader/static-ffmpeg binary is fully static and cannot dlopen libva
  backend plugins (the Mesa .so driver files that VAAPI requires), so VAAPI
  always failed with "Device creation failed: -12" regardless of what runtime
  libraries were installed. The fix uses a dual-binary approach: the static
  build (/usr/local/bin/ffmpeg) is used for CPU and CUDA modes, while VAAPI
  mode explicitly calls the system ffmpeg package (/usr/bin/ffmpeg), which is
  dynamically linked and correctly loads mesa-va-drivers at runtime. Both
  binaries are now installed in the container.

### 0.5.9
- Fix: VAAPI hardware acceleration (FFMPEG_HWACCEL=vaapi) now works correctly.
  The previous Docker image was missing the VA-API runtime libraries that the
  static ffmpeg binary requires at startup (libva2, libva-drm2, mesa-va-drivers).
  Without them ffmpeg silently failed with "Device creation failed: -12" and
  marked every scene as an error. These packages are now installed in the runtime
  stage of the Dockerfile. AMD integrated GPU users should rebuild the image.
- Note: scenes marked as errors due to a broken VAAPI setup can be retried by
  starting a new fingerprint generation job from the Operations tab. New jobs
  (started without a cursor) always retry error records while skipping scenes
  that were already successfully fingerprinted.

### 0.5.8
- Feature: New FFMPEG_HWACCEL environment variable controls hardware-accelerated
  frame decoding. Set to "cuda" for NVIDIA (NVDEC), "vaapi" for AMD or Intel
  (VAAPI via /dev/dri/renderD128), or "none" (default) for CPU decoding. When
  enabled, large frame buffers for high-resolution files stay in GPU memory
  rather than host RAM, reducing OOM crashes on 4K+/HEVC content. Both compose
  files include the new variable (defaulting to "none") with commented-out AMD
  and Intel device mappings. See README for full setup instructions.
- Note: hwaccel reduces memory pressure but adds per-frame GPU context init
  overhead. CPU mode remains faster for normal 1080p/4K libraries.

### 0.5.7
- Fix: Docker image now ships with a modern static ffmpeg build (mwader/static-ffmpeg
  latest) instead of Ubuntu 22.04's bundled ffmpeg 4.4.2 (2021). The newer build
  includes improved HEVC/10-bit decoding, better memory efficiency for large
  high-resolution files, and up-to-date codec support. This may reduce OOM crashes
  on very large files (e.g. 7K HEVC 10-bit scenes) that previously caused the
  ffmpeg subprocess to be SIGKILL'd by the kernel OOM killer.

### 0.5.6
- Fix: Duplicate Scene File Detection (and all other analyzers) no longer crash
  with "'utf-8' codec can't decode byte" when the Stash library contains files
  whose paths include non-UTF-8 characters (e.g. Latin-1 accented filenames like
  'é'). The Stash GraphQL client now decodes HTTP responses with errors='replace'
  instead of strict UTF-8, so a handful of garbled characters in a file path no
  longer aborts the entire request.

### 0.5.5
- Fix: Fingerprint generation crash loop now fully resolved. The previous fix
  wrote an error record only inside Python exception handlers, which do not run
  when the Docker container is killed by SIGKILL. Now an error record is written
  to the database *before* each scene is processed. If the sidecar is SIGKILL'd
  mid-run, the error record persists and skip_errors=True (active on crash
  recovery) skips the scene rather than retrying it indefinitely.
- Fix: Clicking Stop or Force Stop on the fingerprint generation job now
  actually stops it. Previously the job returned a resumption cursor in all
  cases, which caused the queue manager to re-queue it immediately. Now the
  queue manager distinguishes user-initiated cancels (request_user_cancel) from
  system shutdown stops (request_stop): user-cancelled jobs are marked
  completed, not re-queued. The cursor from the last batch checkpoint is
  preserved so a manual restart can resume where it left off.

### 0.5.4
- Fix: Fingerprint generation no longer enters an infinite crash loop when a
  scene repeatedly fails. Previously, connection and exception failures did not
  write an error record to the database, so the offending scene was retried on
  every restart. Error records are now written for ALL failure types (non-200
  HTTP, timeout, and exceptions). When resuming from a crash cursor, scenes with
  an existing error record are skipped so the job can advance past them.
- Fix: When fingerprint generation is interrupted mid-run (graceful stop or
  shutdown), the job is now re-queued for resumption rather than incorrectly
  marked as "completed" in the job history.
- Fix: ffmpeg frame extraction failures are now logged at WARNING level with the
  full ffmpeg stderr output, making it possible to diagnose why specific scenes
  fail without enabling debug logging globally.
- Fix: `asyncio.CancelledError` raised by a finished task no longer silently
  breaks the queue dispatch loop's completed-task check.
