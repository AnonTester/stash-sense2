## 2026-08-22

### 0.14.0
- Remove: tattoo and body-proportion identification signals, entirely.
  A real matching-accuracy benchmark (100 tattoo-tagged scenes, a real
  reference embedding index) found tattoo signal never measurably
  helped identification and slightly hurt it even after two rounds of
  fixes (better reference photos, narrower fusion weighting) -- see
  0.13.5-0.13.7. Body-proportion matching never had any reference data
  populated by any part of the pipeline in the first place (confirmed:
  every fingerprint ever logged "0 body" performers), so it never did
  anything either. Removed: the tattoo detector/matcher and body
  extractor, the "Tattoo Detection"/"Body Proportions" Settings toggles,
  `tattoo_yolov5s`/`tattoo_clip_vitb32` from the downloadable models list
  (and their GitHub release assets), the `use_body`/`use_tattoo`/
  `use_multi_signal` request fields and `signals_used`/`tattoos_detected`
  response fields on every identify endpoint, and the tattoo embedding
  count shown in Settings. Scene fingerprinting is unaffected -- it only
  ever needed face detection+embedding for its fast-path cache, never
  body/tattoo data.

### 0.13.7
- Change: tattoo signal now nudges face-match ranking within roughly
  +-8% instead of the old 0.7-1.5x range -- a real matching-accuracy pass
  found the wider range net-negative (it moved very few scenes, and
  every move was neutral-to-harmful, including flipping at least one
  already-correct face match to a wrong one). Tattoo signal was always
  meant as a corroborating/tie-breaking signal, not a strong identifier
  on its own; the multiplier range now reflects that. Also softened the
  "candidate has no reference embedding" case from an outright penalty
  to a mild one -- absence of a reference embedding usually just means
  nobody's built one yet, not evidence the candidate lacks a tattoo.

### 0.13.6
- Change: the tattoo detector now loads whenever its model file is
  installed, regardless of the "Tattoo Detection" Settings toggle. That
  toggle now only controls whether tattoo data is *used* for matching --
  detection+embedding already ran as a side effect of scene fingerprinting
  for every scene either way, so a fingerprint built before you turn the
  toggle on now already has tattoo data cached, instead of needing every
  scene re-fingerprinted from scratch.
- Change (`Dockerfile.rocm`): `HSA_OVERRIDE_GFX_VERSION` is no longer
  baked into the ROCm image -- one value can't be right for every AMD
  card. It's now a `docker-compose.rocm.yml` environment variable
  (defaults to the reference deployment's `11.0.0`), so it can be set per
  card without rebuilding.

### 0.13.5
- Add: the plugin now warns when the sidecar container is running an
  older version than this JS needs. The identify button's status dot
  turns orange (distinct from the red "disconnected" state) and its
  tooltip names the running/required versions when the sidecar is
  reachable but out of date; a matching console warning is also logged.
  Update the sidecar container to clear it.
- Fix: tattoo detection never actually ran, regardless of the
  `use_tattoo` request flag or the "Tattoo Detection" Settings toggle --
  startup wrongly required a tattoo *matching* index (which nothing has
  ever populated) before it would even construct the *detector*, so the
  YOLO model was never loaded. Detection and matching are now decoupled:
  the detector loads whenever its model file is installed, independent
  of whether reference embeddings exist for matching on top of it. A
  `use_tattoo=True` request against a sidecar where the detector still
  isn't loaded (toggle off, or model not installed) now surfaces a clear
  error in the response instead of silently reporting zero tattoos found.

### 0.13.4
- Add: "Idle Unload Timeout" setting (Settings -> Performance) controlling
  how long face recognition sits idle before being unloaded from memory
  (freeing it up, at the cost of a reload delay on the next request).
  Previously hardcoded at 30 minutes with no way to change it; now
  defaults to 60 minutes and can be set to 0 to disable idle unloading
  entirely (keep it loaded once started, until the sidecar restarts).
  Takes effect live, no restart needed.

### 0.13.3
- Add: performers discovered via a non-stash-box catalogue source (e.g.

### 0.12.24
- Fix: Adding a performer from the Identify modal while a scene/image/
  gallery edit tab was open always mutated the entity directly via GraphQL,
  even though that tab's own Save button resubmits its entire performer
  list -- meaning a later Save could silently revert the addition. The

  reloads automatically after the direct mutation (previously it didn't
  reload in that case at all, leaving the Details-tab cover stale).
  Also fixes a related latent bug this change would otherwise have made
  much worse: the "is an edit tab open" check only looked for a Save
  button anywhere in the DOM, but Stash's tabs (Details/Edit/Markers/...)
  stay mounted after switching away -- so once a scene's Edit tab had
  been visited even once, its now-hidden Save button kept being found
  from every other tab for the rest of the page's lifetime. Confirmed
  live: this caused an add clicked from the Details tab to silently
  stage into the hidden, inactive Edit tab instead of mutating directly,
  with no visible feedback at all. The check now also requires the Save
  button to actually be visible (`offsetParent !== null`).

## 2026-08-16

### 0.12.15
- Fix: Local performer matches could be scored using only a single model
  (FaceNet or ArcFace) whenever the other model didn't rank the candidate
  at all -- common for the local index given its much smaller candidate
  pool (~1-2k) compared to the main database (~450k). Trusting a single
  model's raw distance as if it were the full combined score, then
  applying the local-match boost on top, could turn a coincidental
  single-model agreement into an artificially high-confidence wrong
  match, displacing the correct (already-tagged) performer. Confirmed
  live on two real scenes: a group scene where a phantom 90% local match
  fragmented what should have been two clean person clusters (the
  correct performers now both resolve correctly, tagged, ~62% each), and
  a single-person scene where a wrong local match at 84% outranked the
  correct tagged performer at 67% (now correctly ranked first at 67%,
  wrong match reduced to 72%). Local matches now require both models to
  agree before being trusted, mirroring the main index's existing
  penalty-for-missing-model handling rather than skipping it.
- Improvement: Local performer matches now show a "View local performer"
  link (opens the performer's page on this Stash instance) instead of a
  plain "in your local library" badge with no way to open/verify the
  match.

### 0.12.7

## 2026-06-05

### 0.5.10
- Fix: VAAPI hardware acceleration now works correctly on AMD and Intel.
  The mwader/static-ffmpeg binary is fully static and cannot dlopen libva
  backend plugins (the Mesa .so driver files that VAAPI requires), so VAAPI
  always failed with "Device creation failed: -12" regardless of what runtime
  libraries were installed. The fix uses a dual-binary approach: the static
  build (/usr/local/bin/ffmpeg) is used for CPU and CUDA modes, while VAAPI
  mode explicitly calls the system ffmpeg package (/usr/bin/ffmpeg), which is
  dynamically linked and correctly loads mesa-va-drivers at runtime. Both
  binaries are now installed in the container.

### 0.5.9
- Fix: VAAPI hardware acceleration (FFMPEG_HWACCEL=vaapi) now works correctly.
  The previous Docker image was missing the VA-API runtime libraries that the
  static ffmpeg binary requires at startup (libva2, libva-drm2, mesa-va-drivers).
  Without them ffmpeg silently failed with "Device creation failed: -12" and
  marked every scene as an error. These packages are now installed in the runtime
  stage of the Dockerfile. AMD integrated GPU users should rebuild the image.
- Note: scenes marked as errors due to a broken VAAPI setup can be retried by
  starting a new fingerprint generation job from the Operations tab. New jobs
  (started without a cursor) always retry error records while skipping scenes
  that were already successfully fingerprinted.

### 0.5.8
- Feature: New FFMPEG_HWACCEL environment variable controls hardware-accelerated
  frame decoding. Set to "cuda" for NVIDIA (NVDEC), "vaapi" for AMD or Intel
  (VAAPI via /dev/dri/renderD128), or "none" (default) for CPU decoding. When
  enabled, large frame buffers for high-resolution files stay in GPU memory
  rather than host RAM, reducing OOM crashes on 4K+/HEVC content. Both compose
  files include the new variable (defaulting to "none") with commented-out AMD
  and Intel device mappings. See README for full setup instructions.
- Note: hwaccel reduces memory pressure but adds per-frame GPU context init
  overhead. CPU mode remains faster for normal 1080p/4K libraries.

  latest) instead of Ubuntu 22.04's bundled ffmpeg 4.4.2 (2021). The newer build

  high-resolution files, and up-to-date codec support. This may reduce OOM crashes
